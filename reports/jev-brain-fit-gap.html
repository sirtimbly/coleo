A guide to a fair replacement trial

Which Brain decisions
can move to JEV?

Several judgment-heavy responsibilities are good candidates. The current evaluator covers only part of the Brain’s work, and the existing switches do not transfer responsibility away from legacy handlers.

Based on the current local implementation. This report changes no settings and runs no actions. Examples below are illustrative, not measured outcomes.

The distinction that matters: an action adapter is not a complete workflow.

JEV can already send a prompt or update a task. That does not mean it has all the evidence, timing rules, and lifecycle behavior of every existing handler that performs those actions. The fit/gap sections below explain those differences.

Follow-up prompts from arm messages

A good first replacement trial

Can the old handler be turned off?

Only the discretionary follow-up branch, after adding an ownership switch.

What the Brain does today

The Brain reads assistant output and stuck-arm signals to decide whether to send another instruction. These paths combine rules, runtime checks, and sometimes model interpretation. A prompt may ask an arm to investigate a problem, report progress, or continue work.

What JEV can cover now

JEV already evaluates whether a prompt is warranted across the shared window. It can select a real arm and one of six prompt purposes: investigate, report progress, continue the task, verify a fix, record completion, or review a conflict. The existing adapter sends a non-interrupting prompt with quoted evidence.

What is still missing

The adapter assembles a fixed instruction; it does not write a tailored explanation or answer an arbitrary technical question. The current snapshot also lacks some live harness and startup-grace information used by legacy handlers. A shared prompt endpoint does not make every prompting workflow equivalent.

What a broad disable would remove

Disabling all prompting would also remove initial instructions, reminders to fetch available work, and permission responses. Those must remain owned by their existing workflows.

Illustrative example

An arm says, “The failing test looks unrelated; I have not investigated it.” JEV could choose investigate and cite that message. If another arm has already identified the cause and the Brain already prompted this arm, it should wait or mark the issue handled.

Smallest useful next change

Separate follow-up decisions from initial assignment, work dispatch, and permission handling. Feed JEV current harness activity and startup-grace facts, then route only these discretionary prompts through the selected engine.

How to judge the bake-off

Replay unresolved issues, already-handled issues, and productive tool-use turns. Compare useful follow-ups, interruptions of productive work, duplicate prompts, and time from the source event to the prompt.

Recognize and log bugs from arm output

A good first replacement trial

Can the old handler be turned off?

The bug-detection decision branch can become JEV-owned; keep the bug API and duplicate checks.

What the Brain does today

Assistant-output interpretation can classify a message as a bug report and create a bug. It shares a processor with task creation and task updates, so turning off the entire processor removes more than bug detection.

What JEV can cover now

JEV has an implemented create_bug action. It can examine multiple arms’ messages alongside existing bugs, decide that a malfunction is new, select evidence and priority, and call the existing bug-creation endpoint.

What is still missing

The title and description are built from source evidence and a fixed template. They may be less useful than a focused description with reproduction steps. Coverage is bounded, so the supplied set of bugs may be incomplete; execution is blocked when configured limits are exceeded.

What a broad disable would remove

Skipping the whole assistant-output processor would also lose new feature-task creation and broader task updates that the swarm evaluator cannot currently perform.

Illustrative example

Two arms encounter the same API error. The desired result is one bug with useful evidence, not one report per arm. A routine tool failure followed by a successful retry should usually produce no bug.

Smallest useful next change

Give bug detection its own decision-owner setting. Preserve the shared bug endpoint, record source identities, and inspect whether the resulting descriptions are useful enough to work from.

How to judge the bake-off

Label real incidents, recovered errors, duplicate reports, and quoted examples. Measure missed bugs, false bug reports, duplicates, correct priority, and report usefulness—not just whether a bug row was created.

Record discoveries and task discussion findings

Good fit for additional observations

Can the old handler be turned off?

There is no blanket replacement here: keep explicit arm submissions and trial JEV’s inferred findings.

What the Brain does today

Arms can explicitly submit discoveries and task discussion comments through existing APIs. The Brain also has access to activity and task state that may contain useful findings nobody has recorded.

What JEV can cover now

Both log_discovery and comment_task are implemented. JEV can notice that a finding in the activity window is worth retaining and attach evidence to a discovery or to a selected task discussion.

What is still missing

Discovery creation currently records a generic pattern with informational severity. Comment text is a fixed wrapper around evidence. The snapshot does not include complete task discussion history, so JEV cannot reliably recognize every point already discussed.

What a broad disable would remove

An arm’s explicit report is an instruction to persist a known record. Disabling that ingestion path would discard intentional reporting, including data not present in the evaluator’s recent window.

Illustrative example

An arm discovers that a recurring test failure depends on a shared fixture. JEV could preserve that observation for other arms. If the arm already submitted the same discovery, the evaluator should not submit it again.

Smallest useful next change

Retain explicit reporting. Add recent discussion content and stable links to existing discoveries before using JEV for broader semantic deduplication.

How to judge the bake-off

Compare useful new findings against redundant comments and low-value noise. Confirm correct task association and that an explicit arm report remains visible even when JEV abstains.

Correct task priority or blocked/pending state

Useful subset of task management

Can the old handler be turned off?

Only priority and narrowly defined pending/blocked judgments; retain the rest of task lifecycle handling.

What the Brain does today

Task-management handlers interpret output, maintain work state, enforce blockers, and apply lifecycle changes. The existing assistant-output schema supports more fields and statuses than the JEV adapter.

What JEV can cover now

JEV can propose a task priority change or a correction between pending and blocked. Execution checks the target version and prevents status changes that override assignment, planning blocks, dependency blocks, or human-review blocks.

What is still missing

There is no JEV adapter for queue position, subject or description edits, assignment, completion, failure, or cancellation. The snapshot contains selected task fields and a bounded set of tasks, not every task and relationship in the system.

What a broad disable would remove

A broad “disable task handling” switch would leave lifecycle transitions and task metadata updates unhandled. It could also remove dependency and claim protection if it skipped entire handlers.

Illustrative example

A pending, unassigned task has fresh evidence of a genuine blocker. JEV may mark it blocked. “Move this refactoring task to the very bottom” is not equivalent: priority alone cannot change its queue order.

Smallest useful next change

Define individual supported changes in the owner settings. Expand candidate fields and execution adapters only when needed, while keeping version, dependency, ownership, and approval checks shared.

How to judge the bake-off

Use labeled reprioritizations and blocked/pending corrections. Include assigned tasks, dependency blocks, human deferrals, and stale snapshots. A correct refusal to change a protected task counts as success.

Update existing bugs

Evidence and priority updates only

Can the old handler be turned off?

The supported evidence/priority decision branches can be isolated; keep resolution and escalation workflows.

What the Brain does today

Bug workflows track state, priority, relationships to blocked tasks, and escalation. Some actions change the bug itself; others change tasks or notify the human.

What JEV can cover now

JEV can select an existing bug, append evidence to its description, and optionally change priority. The patch uses a version precondition so a newer edit is not silently overwritten.

What is still missing

The adapter cannot resolve or reopen a bug, assign it, maintain blocker relationships, or run the complete escalation process. The snapshot lacks the full relationship and escalation history those workflows use.

What a broad disable would remove

Turning off bug workflows as a unit could leave fixed bugs unresolved, tasks blocked after a fix, or overdue escalation unhandled. Appending evidence does not complete those workflows.

Illustrative example

A second arm reports a reproducible instance of an existing bug. JEV can attach it. A statement that the bug is fixed should lead to verification; the current adapter cannot validate and close the bug.

Smallest useful next change

Separate evidence enrichment and priority judgment from lifecycle transitions. Supply blocker relationships and prior escalation records before expanding ownership.

How to judge the bake-off

Check correct bug matching, relevant evidence, priority changes, and preservation of concurrent edits. Track repeated description additions as a quality failure even if all API calls succeed.

Nudge idle arms toward available work

Prompt capability exists; dispatch context is missing

Can the old handler be turned off?

Keep existing work-availability and initial-instruction handling for the first trial.

What the Brain does today

promptIdleArms() loads pending/claimed tasks, determines which are available to an arm, checks live harness state and recent activity, and consults the arm state machine. It can then prompt an arm to fetch work.

What JEV can cover now

JEV can recognize an idle arm with relevant recent evidence and send a continue-task or progress prompt. It can also consider other arms’ activity and previous Brain interventions.

What is still missing

The JEV snapshot does not provide the complete eligible backlog, all queue ordering and ownership context, or all runtime checks. Old, unassigned pending tasks may be omitted. With no non-Brain events in the window, the evaluator returns without making decisions.

What a broad disable would remove

An arm could sit idle while real work is waiting, especially when both the task and the last arm message are older than the window. Disabling initial instructions could prevent a newly spawned arm from starting at all.

Illustrative example

A task has waited overnight and an idle arm has been silent for ten minutes. A five-minute message window may contain neither the task nor usable evidence to trigger a prompt.

Smallest useful next change

Add an explicit eligible-work summary and observed runtime/progress timestamps. Support state-based decisions with no new messages. Preserve deterministic eligibility checks and initial delivery.

How to judge the bake-off

Include an empty event window, old pending tasks, recently started arms, busy harnesses marked idle in the database, and tasks reserved by another arm. Measure time until eligible work actually starts.

Detect stalled, looping, or silent arms

Strong semantic use case; incomplete observation today

Can the old handler be turned off?

Do not turn off whole stuck/health handlers yet. Extract the judgment and retain observation and state repair.

What the Brain does today

Legacy stuck detection, idle-loop detection, and a separately scheduled health monitor inspect activity and runtime state. These paths can escalate through prompts and other interventions; some also synchronize state or detect completion.

What JEV can cover now

JEV can compare messages across arms and distinguish an unresolved loop from productive progress or a problem another arm already handled. Prompt, stop, and human-notification adapters are available.

What is still missing

Silence is not fully represented as structured evidence. JEV needs last productive activity, last heartbeat, runtime state, startup grace, and elapsed time since previous interventions. A rolling message window alone loses long-running incidents, and an empty window currently skips evaluation.

What a broad disable would remove

Long-silent arms may become invisible to the decision path. Turning off an entire handler can also remove state reconciliation and silent-completion handling. The independent health timer can still act unless it honors the same owner selection.

Illustrative example

An arm repeats the same failed command five times: JEV has evidence to judge a loop. An arm emits nothing for twenty minutes: JEV needs explicit elapsed-time and runtime facts, not merely an absence of messages.

Smallest useful next change

Retain observation collectors, persist incident/progress facts beyond the window, and introduce one decision-owner gate shared by the poll and timer callbacks.

How to judge the bake-off

Replay productive long tasks, repeated failures, quiet healthy arms, stopped harnesses, and missing telemetry. Score missed stalls and interruptions of productive work separately.

Stop or recover an unhealthy arm

Stop is implemented; recovery is not equivalent

Can the old handler be turned off?

Only a specifically defined stop decision could transfer. Keep recovery and permission workflows.

What the Brain does today

Existing health/stuck handling can prompt, request compaction, escalate, and stop or mark arms stopped. Permission responses are another path. These operations have different effects even when they all look like “recovery.”

What JEV can cover now

JEV has a stop_arm adapter that calls the existing kill endpoint, checks the target version, and requires a higher execution score. Prompt and stop share an intervention scope to prevent immediate repeated intervention.

What is still missing

There is no equivalent JEV recovery sequence for compaction, restart, or permission decisions. Some existing “kill” callbacks update recorded arm state, whereas the JEV adapter calls the kill endpoint. Those are not necessarily the same operation.

What a broad disable would remove

Replacing the whole recovery handler with stop_arm could escalate directly to termination where the existing workflow would try a smaller intervention. Removing permission handling can leave arms waiting indefinitely.

Illustrative example

A context-exhausted arm may need compaction rather than termination. JEV’s current choices can propose a follow-up or stop, but they do not implement the full compact-and-observe sequence.

Smallest useful next change

Define shared operational semantics for stop, interrupt, compact, and restart. Add the missing observed state and adapters before comparing recovery sequences. Keep permission policy independent.

How to judge the bake-off

Measure successful recovery, time to productive work, unnecessary stops, and preserved task state. Test uncertain transport outcomes and verify that a lost acknowledgement does not cause a second intervention.

Missing capability

Detect silent task completion

No equivalent completion capability

Can the old handler be turned off?

No. Keep validated completion handling, even if stuck-message interpretation moves to JEV.

What the Brain does today

checkStuckArms() includes a path for detecting an arm that appears finished without having called the normal completion tool. Existing handling can then enter the task-completion workflow.

What JEV can cover now

JEV can infer that a follow-up is warranted and prompt the arm to record completion or verify a fix. This is useful assistance but does not itself complete the task.

What is still missing

The swarm action set has no complete_task action. It lacks a dedicated contract for validation results, completion artifacts, and downstream lifecycle effects. A message saying “done” is not sufficient proof.

What a broad disable would remove

Tasks can remain busy or incomplete after their arm stops producing work. Removing the whole stuck handler to test JEV would silently remove this recovery path.

Illustrative example

An arm reports “All tests pass; the change is committed” and goes idle. JEV can ask it to record completion. It cannot currently confirm those claims and safely finalize the task itself.

Smallest useful next change

First decide whether JEV should only request completion or also recommend a validated completion transition. For the latter, supply observed validation/artifact state and route through the existing completion workflow.

How to judge the bake-off

Include genuine completion, premature claims, failing validation, uncommitted work, and lost completion messages. Measure correct finalization and false completion separately.

Review and escalate blocked tasks

JEV can judge urgency; the scheduling workflow is missing

Can the old handler be turned off?

Keep the review scheduler and escalation state. A narrower urgency or priority judgment could transfer later.

What the Brain does today

reviewBlockedTasks() selects due tasks, chooses idle review arms, records review ownership and a lease, and reads discussion context. Escalation handling considers blocker age, linked bugs, and previous escalation levels.

What JEV can cover now

JEV can see some blocked-task and bug state, recommend a priority correction, add a discussion finding, or notify the human through an arm-associated candidate.

What is still missing

It does not schedule reviews, reserve review arms, renew leases, or maintain escalation stages. The snapshot omits important review dates, discussions, bug-blocker relationships, and escalation records. Human notification candidates are currently arm-based, not task-based.

What a broad disable would remove

Blocked tasks may never get a reviewer or a scheduled recheck. Removing the workflow also loses ownership and escalation bookkeeping; a generic prompt does not replace a leased review assignment.

Illustrative example

A task has been blocked for two days by a bug. The existing workflow can assign an available arm to review it. JEV may recognize urgency, but it cannot currently create that review reservation and maintain its lifecycle.

Smallest useful next change

Expose review due dates, leases, linked blockers, and prior escalations. Let code select eligible review slots; trial JEV’s judgment of review value or urgency within that workflow.

How to judge the bake-off

Use overdue and not-yet-due tasks, existing review leases, repeated escalations, human-deferred tasks, and resolved blockers. Measure time to unblock and reviewer duplication.

Classify direct human messages

A separate integration is needed

Can the old handler be turned off?

No. Keep human-mail ingestion and action routing until the historical classifier is wired into that path.

What the Brain does today

processHumanMail() interprets direct messages and routes the resulting intents. It owns a different responsibility from scanning a swarm activity window: carrying out what the human asked, with the right thread context.

What JEV can cover now

The earlier JEV classification experiments establish a place to compare message interpretation. Typed choices are suitable for identifying one or more intended actions and then selecting their arguments.

What is still missing

Those experiments are not the live swarm evaluator’s human-message router. A replacement needs quoted-thread context, multi-action extraction, entity resolution, field extraction for the selected schemas, and a follow-up policy for ambiguity. The current swarm schema cannot express all of those actions.

What a broad disable would remove

Direct instructions could be ignored or only produce a generic observation. “One feature plus one bug” must not collapse into a single action, and a task deferral must not be mistaken for approval or rejection.

Illustrative example

“Move that refactoring task to low priority and the bottom of the queue” requires resolving the quoted task, changing priority, and changing queue position. The swarm adapter can only cover the priority part.

Smallest useful next change

Integrate a dedicated JEV intent classifier behind the existing human-message handler. Keep message acknowledgement and action validation in code. Use the human-labeled historical cases before enabling execution.

How to judge the bake-off

Compare action-set accuracy and extracted fields, not just top-level labels. Include the feature-plus-bug message, the quoted reprioritization, and “Only prompt arm default.” Track unnecessary clarification questions.

Keep existing

Planning, claims, dependencies, NATS, and infrastructure

Keep the operational foundation in code

Can the old handler be turned off?

No blanket disable. Preserve the mechanisms that establish state and enforce policy.

What the Brain does today

Planning gates decide whether work may start. Queue consumers ingest explicit messages. Claims and dependencies constrain task eligibility. State transitions, persistence, and infrastructure checks keep the swarm coherent and available.

What JEV can cover now

JEV can contribute selected judgments inside these workflows—for example, whether evidence warrants a follow-up. It depends on the same infrastructure to receive events, inspect state, record decisions, and execute an action.

What is still missing

The evaluator is not a substitute for message delivery, claim ownership, dependency enforcement, durable writes, or service recovery. Dev-server restart and Git preservation have choice types but remain proposals; verified execution adapters are absent.

What a broad disable would remove

Disabling these mechanisms could make the evaluator’s snapshot incorrect or unavailable and remove the checks that keep its actions valid. It would also change the experiment’s foundations, making the two approaches incomparable.

Illustrative example

A task depends on unfinished work. Code should keep it ineligible regardless of which model thinks it looks important. A failed dev server can be noticed by JEV, but recognition alone does not restart the right process safely.

Smallest useful next change

Retain the shared execution and policy layer. For future dev-server or Git actions, add managed process/worktree identity, precise operations, and observed outcomes before enabling execution.

How to judge the bake-off

Assert invariants in both experiment arms: no conflicting claims, no bypassed dependencies or human gates, no duplicate reserved effects, and preserved work after transport failures.

Proposed controls · not implemented

Make ownership explicit.

Use one decision-owner selection for each responsibility. That lets you test JEV without removing the rest of the Brain or allowing two handlers to compete over the same incident.

SelectionWho decides and acts?What it measures
ExistingThe existing decision path owns this responsibility.Baseline behavior and cost.
CompareBoth evaluate the same state before effects. Only the existing path executes.Decision agreement, missed opportunities, and decision latency. JEV’s alternative real-world outcome is still unobserved.
JEVJEV owns the selected responsibility; the corresponding legacy decision branch is skipped.Actual intervention quality and time to resolution. Shared guards and execution still apply.

Start with message-driven follow-ups and bug detection. Discoveries and discussion findings are useful additional coverage. Keep task creation/completion, initial instructions, work dispatch, permission handling, and infrastructure recovery on their existing paths.

  1. Separate observation from intervention. Keep collecting runtime state and events. Extract mixed decision branches instead of skipping whole handlers.
  2. Use one owner everywhere. The separate health-monitor timer and delayed callbacks must obey the same policy as the poll loop. Changing a setting must also prevent pending actions from the previous owner.
  3. Compare on a common starting snapshot. Evaluate before either path acts. A JEV decision made after a legacy fix is not a fair comparison with the decision that caused that fix.
  4. Make failures visible. Distinguish “no action needed” from missing context, low score, timeout, or an unavailable model. If a live fallback is desired, label every fallback action so it does not count as a JEV success.
  5. Progress from replay to controlled execution. Use labeled historical windows first, then comparison mode, then a bounded JEV-owned trial. Cross-arm effects make independent per-arm A/B assignment unreliable; use whole-swarm periods or isolated scenarios and record their differences.

Measure speed end to end

Record event time, snapshot time, decision start/end, reservation, dispatch, acknowledgement, and observed resolution. Report median and tail latency, total poll duration, model/API cost, and coverage by responsibility.

Measure usefulness as well as activity

Label correct actions, missed actions, unnecessary prompts, duplicate issues, productive work interrupted, and time to recovery. More actions is not necessarily better; fewer actions may mean good restraint or missed responsibility.

Current implementation limits

Read the result with these limits in mind.

  • Speed opportunity: replacing serial model interpretation may shorten a poll. Replacing a simple deterministic check with a network call is unlikely to help. No end-to-end replacement speedup has been established by this report.
  • Window: the default is 10 polling intervals—five minutes at a 30-second interval. Older incidents need explicit persisted state; a rolling window is not complete memory.
  • Silent windows: the evaluator currently returns no proposals when there are no non-Brain events. That is a coverage gap for silence-driven responsibilities.
  • State coverage: JetStream events are not full harness transcripts. The snapshot omits full task discussions, the complete old task backlog, and several lifecycle/runtime fields. Explicit limits include 1,000 raw events and 100 relevant tasks, bugs, and discoveries each; event bodies are capped at 2,500 characters.
  • Execution gates: incomplete coverage blocks execution. Oversized queries fail at a conservative 100,000-character guard. These cases must count as uncovered evaluations, not correct abstentions.
  • Work per evaluation: routing is followed by a detail request when needed. At most eight candidates proceed to detail selection, and only one effect per target is dispatched per poll.
  • Scores: execution requires at least 0.90, or 0.98 for stopping an arm, using the minimum of selected route/detail probabilities. This is not a calibrated probability that the whole workflow is correct. Thresholds need evaluation on Coleo incidents.
  • Repeat prevention: durable reservations, cooldowns, new-evidence checks, and unresolved-result blocking stay in place for both approaches. Conservative at-most-once dispatch can leave an uncertain action needing reconciliation.
  • History: JEV recommendations already appear in Inbox → Brain → Decisions, including proposals and outcomes. A fair comparison additionally needs matching legacy decisions, timing, fallback attribution, and outcome labels.

Design guidance: TypeSafe’s building guide separates model judgments from code-owned execution. Its confidence guidance recommends thresholds tuned to the action and domain. Repository paths in each item identify the local implementation reviewed here.
