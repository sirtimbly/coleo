## Release blockers and acceptance criteria

Items 1–2 are failing release paths. Items 3–6 are distribution/contract gates. Items 7–8 are concrete state-safety gaps worth fixing before stable release. The lifecycle scope decision in the following section must also be resolved before release claims are finalized.

### 1. Repair version propagation in the release PR — confirmed failure

PR #117 updates package manifests to `1.0.0` but does not update `uv.lock`. CI reports: `uv.lock client version is 0.14.4; expected 1.0.0. Run uv lock.` The Python locked installation also fails. This blocks the test, Python, and browser jobs before meaningful release validation.

**Do:** regenerate the lockfile for the release candidate and fix the release automation so subsequent version bumps remain synchronized.

**Done when:** `versions:check`, locked Python installation, and all candidate CI jobs pass on the exact commit to be tagged.

Evidence: `release-please-config.json:11`, `server/src/scripts/check-versions.ts:40–45`, `uv.lock:28–29`, PR #117 changed-file list and failed logs.

### 2. Fix the Arm Host container build — confirmed failure

`Dockerfile.cloudflare-agent:5–10` copies root manifests and `server/src`, but omits `server/package.json`. `server/src/version.ts:1` imports `../package.json`, producing the observed bundle failure. In the repository that manifest is a symlink to the root manifest; it is absent from the container build layout.

**Do:** make the container build layout resolve that import and validate both release images before publication. Add a pre-release build check so this cannot remain hidden behind green application CI.

**Done when:** both images build and smoke successfully, and the associated `reef-release.json` is generated and attached. Its publishing job depends on successful image publication (`.github/workflows/publish-cloudflare-container.yml:137–161`). If this topology is excluded from 1.0, explicitly remove it from the supported release promise.

### 3. Validate assembled, installed release artifacts — coverage gap

The component workflow runs platform smoke checks before receiving the separately built web artifact. Assembly generates manifests without repeating installed-artifact smoke, so the web-specific smoke branch is not exercised by this workflow.

**Do:** test the final assembled archives in clean environments, including the web artifact with its private runtime dependencies. Exercise install, version/help, API start/auth, web connection, Python client, upgrade, and uninstall behavior on every advertised OS/architecture. Run macOS build/tests and require signed/notarized artifacts if native macOS is stable in 1.0.

**Done when:** a candidate artifact matrix records checksums, versions, successful installation/startup, and supported platforms. Stage this evidence before announcing availability; component publishing currently starts after release publication while npm publishes independently.

Evidence: `.github/workflows/publish-components.yml:69–102,104–106,174–208`, `server/src/scripts/smoke-component-artifacts.ts:40–82`, `.github/workflows/publish-npm.yml:3–12`.

### 4. Publish and rehearse the breaking-change migration — documentation and validation gap

`docs/guides/workspace-client.md:109–128` still says existing Bun commands remain available and scripts should retain the old executable. Migrated command handlers instead print migration guidance and fail (`server/src/cli/client-migration.ts:15–19`). Existing installation guidance does not constitute a complete data migration/restore rehearsal.

**Do:** produce one authoritative 0.14.4 → 1.0 guide covering:

- Old/new executable and command mapping: operator, server, agent, Python client, separately hosted web UI.
- Service shutdown/startup order, environment/config precedence, client URLs and credentials.
- Backup of persistent state and configuration; upgrade against representative populated databases, including the new `073_hosts` migration.
- Verification that tasks, plans, messages, profiles and host inventory survive; recovery from interrupted upgrades.
- A tested restore procedure and explicit limits on downgrading a migrated database.

**Done when:** a clean installation and an existing-user upgrade can be completed from the guide alone, and backup restoration is demonstrated. Existing migration unit tests are useful evidence, not a substitute for this release rehearsal.

### 5. Reconcile documented safeguards with implemented behavior — confirmed contract gap

The passing master test run includes 19 TODOs explicitly documenting missing behaviors: content-based secret/commit scanning, domain allowlisting and body inspection, several destructive/exfiltration patterns, and response actions. Meanwhile `docs/architecture/security.md` describes these as current protections, including scanning before any commit.

**Do:** decide which protections belong in the 1.0 contract. Implement and test those promises, and clearly move the remainder to future work. Verify the supported harnesses actually invoke the protections being promised; passing a permission-engine unit test alone does not prove end-to-end interception.

**Done when:** published behavior claims match executable tests and supported harness behavior. This does not require building every proposed detector before 1.0; it requires an accurate support contract.

Evidence: `server/src/brain/__tests__/permission-engine.test.ts:12–21,85–97,268–453`; `docs/architecture/security.md:15–45,48–102,104–208`.

### 6. Finalize license metadata and ship the license — confirmed packaging gap

`LICENSE.txt` still includes `[Your Name]` at line 9 and a placeholder licensing URL at line 32. Its change-date annotation also needs reconciliation with the intended release date. Operator/web archive construction and native app bundling do not explicitly include the license, despite the text's distribution requirement at line 50.

**Do:** finalize the release's license parameters/contact URL, add consistent Python license metadata, and include the license in each distributed component.

**Done when:** inspection of actual npm, Python, operator, web, and macOS artifacts finds the intended license and correct ownership/version metadata.

Evidence: `LICENSE.txt:5–32,50`; `server/src/scripts/package-components.ts:63–87`; `clients/macos/scripts/make-app.sh:20–27`; `pyproject.toml:1–6`.

### 7. Reject incompatible profile imports before changing saved state — confirmed code gap

Exports declare `schemaVersion: 1`, but the import route never validates the bundle's schema version. It then upserts the target profile and deletes/recreates its views and layouts. A transaction rolls back thrown errors; it does not protect against accepting a future-version bundle and silently retaining only the understood subset.

**Do:** validate schema compatibility and the complete supported bundle before replacement. Unsupported future versions must leave existing profiles, views and layouts untouched.

**Done when:** tests prove an incompatible import is rejected without any persisted changes, and supported import/copy flows still round-trip correctly.

Evidence: `server/src/api/routes/workbench.ts:310–407`; accepted requirement in `docs/workbench/review/implementation-plan.md:447–456`.

### 8. Complete browser preference save ordering and failure recovery — inspected timing risk

The preference hook debounces requests but does not serialize in-flight saves. Every request clears the dirty flag in `finally`, including failed or older requests. The hook exposes no saving/error/retry state. This permits stale completions to interfere with newer edits; this review did not reproduce the race at runtime.

**Do:** serialize or revision-guard saves, preserve newer dirty state, retain the last confirmed state, and surface failure/retry behavior. Test rapid edits, delayed/out-of-order responses, save failure, and profile changes during a save.

**Done when:** an older or failed request cannot silently mark newer edits saved or overwrite them.

Evidence: `clients/web/src/workbench/use-view-preferences.ts:24–54`; `clients/web/src/workbench/profile-context.tsx:67–90`; accepted requirement in `docs/workbench/review/implementation-plan.md:253–267`.

## What the plans still require—and what should gate 1.0

### The largest product decision: supervised tasks or the full branch lifecycle?

Accepted ADR-014 requires implementation, review, polish, human approval and merge to remain passes on the original task, with durable single-use leases and deterministic completion gates. The current code still releases a worker and patches the task separately, and creates ordinary QA child tasks. Reviewer/timestamp fields are not the specified atomic pass/lease model.

Evidence: `.project/decisions/014-branch-centered-task-lifecycle.md:23–62`; `.project/plan.md:386–405`; `server/src/brain/brain.ts:3252–3289,8383–8442`; `server/src/api/routes/tasks.ts:1448–1468`.

**Decision required:**

- If 1.0 promises autonomous, lease-safe reviewed-and-merged completion, the durable lifecycle is a substantial remaining implementation gate. Include migration of existing review child tasks and tests for stale/duplicate completion, review ownership, human approval and merge eligibility.
- If 1.0 promises supervised orchestration with the current task/QA workflow, explicitly defer ADR-014 enforcement and document what “completed” means today. This is the recommended narrower release boundary.

Related policy conflict: `.project/plan.md:428–434` says human comments are passive, but `server/src/api/routes/task-discussions.ts:246–260` advances blocked-review eligibility and clears `blocked_needs_human`. Decide the intended behavior and align code, documentation and tests.

The plans contain valuable requirements but mixed timelines. `.project/plan.md:55` still calls for shadcn conformity, `docs/workbench/README.md:12–18` describes relocation as future work, and `.project/status.md:100–115` mixes historical gaps with later-delivered implementation. ## Release acceptance beyond the existing CI suite

These are recommended gates where this review did not find current release-candidate evidence, not claims that the functionality is broken.

1. **Core orchestration:** demonstrate plan preparation → handoff → arm assignment → completion → human review, with the supported harness/provider combinations. Record output quality, failures and recovery, not only process exit codes.
2. **Recovery:** exercise API/brain/arm restart, NATS disconnect/reconnect, WebSocket catch-up, and duplicate-event handling with real persistent state. Run the existing regression and topology suites with required dependencies present; optional NATS skips are not distributed-release evidence (`server/src/regression/smoke-topology.ts:7–13`).
3. **New service controls:** rehearse managed and externally managed APIs, blocked restart with active harnesses, database switching, changed API addresses, and reconnecting clients. The new API tests inject a restart callback; add evidence for the actual detached replacement process (`origin/master:server/src/api/__tests__/hosts.test.ts:108–145`, `server/src/api/routes/services.ts:135–177`).
4. **Cross-client consistency:** run the same populated profile in web/Python/macOS, switch profiles while requests are in flight, reconnect after downtime, and verify task/message selection, edits and attention state stay scoped correctly.
5. **Compatibility policy:** state supported OS/runtime versions, client/server version combinations, API/JSON/schema stability, experimental features, and deprecation policy before labeling interfaces 1.0.
6. **Release enforcement:** require candidate status checks before merge. The active default-branch ruleset requires PRs and prevents deletion/non-fast-forward changes, but contains no required-status-check rule (GitHub ruleset `18721141`, inspected November 5).

## Recommended execution order

1. Fix release version synchronization and container packaging first; obtain a buildable candidate.
2. Freeze the 1.0 support boundary—especially task/pass lifecycle and native-client scope—and reconcile plan/security/documentation claims.
3. Fix profile import compatibility and browser preference persistence.
4. Complete artifact installation and existing-user migration/restore rehearsals.
5. Run orchestration, recovery, and cross-client acceptance on that exact candidate; retain results.
6. Finalize license, migration notes, known limitations, and release assets; require green candidate checks.
7. Tag and announce only after all promised artifacts are available and downloadable.

**Go/no-go rule:** no known failing supported distribution path; green checks on the actual release commit; verified installation and data upgrade/restore; tested core orchestration and recovery; documentation that accurately describes the stable scope.
